# 防护识别：先看清对面是什么，再决定怎么打

> 来源：本表是**自有整理的事实性信号**（cookie 名 / header 名 / URL 片段 / 响应文本），
> 取自公开厂商文档与本项目实际观测到的响应。上游 [`scrapfly/Antibot-Detector`](https://github.com/scrapfly/Antibot-Detector)
> 是 **NPOSL-3.0**（不是 MIT），仅作交叉核对，**不复制其代码或数据文件**。
> 它是浏览器扩展，能看 DOM/JS hook；我们只能看 HTTP 响应，所以只采用**服务端可见的四类信号**。

## 一、为什么需要它（真实痛点）

我们有四条求解路线（纯协议 cfsolve / Camoufox / pydoll / FlareSolverr），但**先决问题是：对面是什么盾？**

| 不看就动手的后果 | 例子 |
|---|---|
| 白跑一次 16–20s 求解 | 目标站其实**没盾**，直接抓就行 |
| 跑错路线 | 站是 **Akamai/DataDome**，而我们的求解只覆盖 CF/AWS WAF |
| 选错产物 | 站是 **Turnstile widget**，要的是 `want=turnstile`，不是 `cf_clearance` |
| 错过最快路径 | 站是 CF 的 **jsd** 老类型 → 纯协议可能直接过，不必上浏览器 |

所以链路应该是：**探测 → 看建议 → 再调用 `/solve`**。

## 二、怎么用

### 命令行（最快的一眼判断）

```bash
python scripts/detect.py https://target/
python scripts/detect.py https://a/ https://b/ --json
```

真实输出（2026-11-01 实测）：

```
https://glassdoor.co.uk/
  状态码: 403   有防护: 是
  · Cloudflare（Anti-Bot, 难度 Medium, 置信度 100）
    证据: header:cf-mitigated, text:_cf_chl_opt, text:/cdn-cgi/challenge-platform/, url:cdn-cgi/challenge-platform/h/g/orchestrate/chl_page/
  CF 挑战类型: managed
  👉 建议: browser — CF managed challenge（静默型，需真实浏览器环境）

https://example.com/
  状态码: 200   有防护: 否
  👉 建议: direct — 未命中已知防护特征——大概率没有盾，直接抓
```

### 服务接口

```bash
# 需要 token；只发一次普通 GET，不启浏览器、不求解
curl -s -X POST localhost:8878/detect -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' -d '{"url":"https://target/"}' | jq .
curl -s "localhost:8878/detect?url=https://target/" -H "Authorization: Bearer $TOKEN" | jq .
```

响应：

```json
{
  "url": "https://glassdoor.co.uk/",
  "status": 403,
  "protected": true,
  "providers": [
    {"id":"detect-cloudflare","name":"Cloudflare","category":"Anti-Bot","difficulty":"Medium",
     "confidence":100,"hits":["header:cf-mitigated","text:_cf_chl_opt"]}
  ],
  "cloudflare_challenge_type": "managed",
  "recommendation": {
    "route": "browser",
    "reason": "CF managed challenge（静默型，需真实浏览器环境）",
    "hint": "用浏览器引擎（默认 Camoufox）"
  },
  "backend": "detect"
}
```

## 三、建议路由的含义

| `route` | 含义 | 你该做什么 |
|---|---|---|
| `direct` | 没命中任何已知防护 | 直接抓，别调 `/solve` |
| `direct_unless_blocked` | 有 CF 但当前响应没有挑战标记 | 先直接抓；被 403 再调 `/solve` |
| `browser` | CF 的 managed/interactive/embedded | `POST /solve`（默认 clearance，用 Camoufox） |
| `pure_protocol_may_work` | CF 的 `jsd` 老类型 | 先试纯协议（`--cfsolve-bin`），失败自动回落 |
| `browser_token` | 检测到 Turnstile widget | `POST /solve` 加 `want=turnstile` + `sitekey` |
| `browser_cookie` | 检测到 AWS WAF | `POST /solve` 加 `want=awswaf` |
| `multicaptcha` | 万盾厂商（Akamai / DataDome / PerimeterX / Arkose / hCaptcha / reCAPTCHA） | **v6.1 起由 `captchas/` 承接**：`recommendation.want` 给出该传的 want（如 `datadome`）；`route=auto` 会自动分发 |
| `unsupported_or_browser` | 命中里**有任何一家**本服务解不了（Kasada / Incapsula / Shape / Sucuri / GeeTest / 腾讯 turing …） | **v6.2 起整页判定为过不去**：拿得到 A 家的凭证也进不去 B 家。文案给出厂商名 + "硬试会白等一个完整超时"的原因。厂商能力表单一事实源在 `solver/vendors.py` |

## 四、覆盖范围与规则来源

- **厂商**：自有整理 **34 个**（11 个 Anti-Bot + 4 个 ANTIBOT + 8 个 CAPTCHA + 11 个 Fingerprint），
  含 Cloudflare / Akamai / DataDome / PerimeterX / Kasada / Shape / Incapsula / Sucuri / AWS WAF /
  reCAPTCHA / hCaptcha / GeeTest / 腾讯防水墙 / Arkose …
- **信号类型**：`cookie`（名，支持 `awswaf*` 尾通配与 `TS01*`/`BIGipServer*` 前缀）、`header`（名）、`url`（只匹配请求 URL）/`content`/`text`（匹配响应体，子串支持 `*` 通配）。
  `solver/detect.py` 的 `SIGNATURES_SOURCE` 记录“自有整理 + 上游仅对照 + 上游许可证 NPOSL-3.0”。
- **动态头规则**：`HEADER_REGEX_SIGNALS` 只匹配 Shape 的 `^x-[a-z0-9]{8}-[a-d]$` 头名（不看头值）；
  Akamai 的 `bazadebezolkohpepadr` 脚本标记作为 content 信号——均按公开观测独立整理。
  `seed=`、`var _=[` 这类过于通用的子串**刻意不收录**：它们会让无盾站被判成有盾。
- **我们额外补的强特征**（见 `solver/detect.py::STRONG_SIGNALS`）：
  `cf-mitigated` 响应头、`_cf_chl_opt`、`/cdn-cgi/challenge-platform/`、`challenges.cloudflare.com`、
  `aws-waf-token`。**为什么补**：上游表里的 CF 特征只有 `__cf_bm`/`cf_clearance` cookie，
  而"挑战页还没下发 cookie"时就会漏判 —— 那恰恰是最需要判断的时刻。
- **CF 挑战类型**：从 `_cf_chl_opt.cType` 或响应特征推断 `managed / jsd / interactive / embedded /
  turnstile`；这一条决定"能不能走纯协议"。

对照上游（只读，不写入）：

```bash
python scripts/gen_detect_signatures.py --check D:\参考项目\Antibot-Detector
```

> `--write` 会显式覆盖本表，但上游是 NPOSL-3.0，默认关闭；只有确认合规路径后才使用。

## 五、限制（必须知道）

1. **只能看 HTTP**：上游扩展能看 DOM、JS hook、window 属性、Canvas 指纹；我们在服务端看不到。
   所以结论是"**大概率有 X 防护**"，不是逐项清单。
2. **只发一次 GET**：有些站要多次导航/交互才会暴露真实防护（例如先给你 CDN 页，交互后才上挑战）。
3. **表会过期**：厂商会改 cookie/header 名；上游在维护，我们跟着重新生成即可。
4. **不能当"安全"用**：`protected: false` 只说明"没命中已知特征"，不代表一定没有盾
5. **`protected` 只看"盾类"（v6.2 修正）**：`Anti-Bot` / `ANTIBOT` / `CAPTCHA` 才算盾；
   `Fingerprint` 类命中（`localStorage` / `navigator.clipboard` / `Intl.DateTimeFormat` …）
   **任何现代站点都有**，不参与 `protected` 判断。此前 `protected = bool(detections)`
   会把这类站判成"有防护"，导致 `route=auto` 对无盾站白起一次浏览器（16–20s / 1.2GB）。
   对应地，只命中指纹类时 `recommendation.route` 是 `direct`（与"什么都没命中"一致），
   不能是 `unsupported_or_browser` —— 否则"有指纹"比"干净"判得更糟
   （可能是未收录厂商，或需要交互才触发）。
