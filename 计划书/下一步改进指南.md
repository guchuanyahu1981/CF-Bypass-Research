### 0.3 v7.0 的主题

**从"能跑"到"可信赖"。**

三条主线，按优先级：

1. **Trust（门禁自洽）** —— 门禁必须能变红、必须覆盖文档承诺的全部路径、文档里的每条命令必须真实存在。
2. **Footprint（冷启动可负担）** —— 把 cfsolve 从"手工编译的私货"变成"可引导装配的一等公民"。**这里优化的是资源与装配摩擦，不是延迟**：`docs/纯协议-cfsolve.md` §六已用源码证明，18–43s 由 CF 下发的 PoW 预算决定，任何方案都要转满同样的时间。
3. **Resilience（出口可保护）** —— 把 `RATE_LIMITED` 这个契约里躺了三个版本的预留码真正落地，给最贵的资源（出口 IP 信誉）装上保险。

外加一条贯穿线：**Experience（交互防回归）** —— 已经把三类交互实测过了，但没有一条用例守着它们。

## 2. 现状判断

### 2.1 已经做对的，不要动

在提出任何改动之前，先把"不能碰"的部分钉死。以下每一条都有真实设计动机，推翻它们等于重赌：

| 决策 | 为什么不能动 |
|---|---|
| **治理挂在入口 + 路由层**（`BackendRouter(governance=)`） | v4.1 实测过：治理放在 `Solver.solve` 里时，只要配了额外后端，守卫/缓存/准入/指标会被整体绕过。这是"缝"而不是"实现细节"。 |
| **2xx 读 `ok`、非 2xx 读 `error_code`** | 这是 Go 客户端与 new-api 对接方共同依赖的契约。求解失败也是 200 + `ok:false`。任何"顺手改成 5xx"的念头都要先看 `solver/errors.py:51-65`。 |
| **`solver/vendors.py` 是厂商能力唯一事实源** | v6.2 的差分 Oracle 当场抓到过"两张表分叉导致假承诺"。合并成一份是修根，不是重构。 |
| **缓存键 = 域 + 出口** | 违反它等于把 A 出口的凭证发给 B 出口，静默 403。`--egress-id` / 代理池标识是这条不变量的实现。 |
| **`docs/facts.json` 单一事实源 + `scripts/validate-docs.mjs`** | 这是全仓唯一"数字不漂移"的机制。要扩展它，不要绕开它。 |
| **前端预算硬上限**（初始 JS 250KB / 3D chunk 260KB / CSS 25KB / 首屏第三方 0） | 已经用 Lighthouse 100×4 兑现过。任何新增依赖都要先过这个预算。 |
| **`captchas/` 是副本不是依赖** | 上游追厂商改版、本项目追 CF；做成副本是为了"我们决定何时 cherry-pick"。不要改回依赖。 |
| **`do_POST` 不拆 `Solver` 类** | 状态机 + 锁 + 队列，拆 = 重写。P3 记录在案，不再论证。 |

### 2.2 真实瓶颈（按对目标的影响排序）

#### 瓶颈一：冷求解的资源成本与装配门槛

先纠正一个容易写错的直觉：**这里的瓶颈不是延迟**。

项目自己的源码级解剖（`docs/纯协议-cfsolve.md` §六）给出了结论：18–43s 的方差主要来自 **CF 服务端下发的 PoW 预算**，浏览器与纯协议都要转满同样的时间；固定可压缩空间只有 ≈1.5–2s（人类行为模拟段）。因此"换个求解器就能快十倍"不成立。

真正的差距在**资源占用与入口门槛**：

| 路径 | 单次耗时（实测） | 资源 | 触发条件 |
|---|---:|---|---|
| cfsolve（纯协议） | **18.43s**（glassdoor 同站 A/B） | **72MB，无浏览器进程** | **当前未配置** |
| Camoufox | 18.74s（同站 A/B；区间 15.87–21.12s） | ~1.2GB + 浏览器进程树 | 默认可用 |
| pydoll（CDP 直连 Chrome） | 60–88s | 中 | 需 Chrome |
| FlareSolverr | 未实测 | — | 需自托管实例 |

两者延迟几乎持平（18.43 vs 18.74），**cfsolve 的价值是"不启浏览器"**：72MB 对 1.2GB，差 16 倍。在 4 worker 的内存预算（≤3.5GB，`docs/项目规格.md` §6 E4）里，这决定了能开几个 worker。

而 cfsolve 的入口被一道编译门槛挡着：`tools/cfsolve-patches/README.md` 要求 MSVC + CMake + NASM + libclang + Rust 工具链，补丁还是本地私货、不是上游支持的行为。`run.bat doctor` 的 WARN 就指向这里。

#### 瓶颈二：出口 IP 信誉

`policy.md` §2 的台账（60/80，失败 3/5）与 R9b（同站连打 12 次后 60s 解不出）说明：**出口信誉是这套系统最贵的资源，且不可再生**。当前系统对它的保护手段只有三条：

1. 同站串行 ≥30s（纪律，非代码）。
2. 换出口必须换 `--egress-id`（纪律，非代码）。
3. 失败即停（纪律，非代码）。

代码侧没有任何"自动刹车"。`ErrorCode.RATE_LIMITED` 在 `solver/errors.py:29` 明确写着"预留值：当前没有按 host 限流，不会产生"。Go 客户端 `gocfsolve/pool.go:42` 却已经把这个码登记成"要 failover 但不是节点的锅"——**契约两端对同一个码的期待不一致**。

#### 瓶颈三：门禁的可信度

三类问题叠在一起：

| 层 | 现状 | 后果 |
|---|---|---|
| 命令层 | `smoke` 默认必红 | "提交前必跑"的链条断在第一环 |
| 聚合层 | `verify` 不含 `doctor`/`smoke`/`bench`，但 `README.md:368` 写「以上全部」 | 执行方跑完 verify 会以为全绿 |
| CI 层 | `.github/workflows/ci.yml` 不跑 `smoke`/`doctor` | 红的那条永远不会在 CI 里暴露 |

### 3.1 P1-01：`run.bat smoke` 在默认鉴权配置下必然失败

#### 现象

```powershell
PS> .\run.bat smoke
...
OK  /health ready（browser=None, cache=None）

  File "...\run.py", line 196, in cmd_smoke
```

#### 证据

- **已验证**：上面的真实执行输出（2026-11-11，本机）。
- **静态确认**：`run.py:168-213` 的 `cmd_smoke` 全文如下（节选关键行）：

```python
def cmd_smoke(a):
    ...
    args = [sys.executable, "solver/service.py", "--port", str(a.port),
            "--cache-dir", str(cache_dir)]
    if a.no_auth:
        args.append("--no-auth")
    proc = subprocess.Popen(args, cwd=ROOT)
    ...
    with urlreq.urlopen(f"{base}/detect?url=https://example.com/", timeout=20) as r:
```

`urlopen` 没有构造 `Request`，也没有带 `Authorization` 头。

- **静态确认**：同一个文件里已经有现成的能力：

```python
def read_env_token():          # run.py:91
    """读 CF_SOLVE_TOKEN：环境变量优先，否则 .env（与 run.ps1 stop 逻辑一致）。"""
```

`cmd_stop`（`run.py:228` 起）已经在用它来带 token 调 `/shutdown`。**`cmd_smoke` 只是漏了复用。**

#### 根因

#### 影响面

1. `README.md:365` 承诺 `.\run.ps1 smoke` 是"全链路冒烟"；`docs/项目规格.md:241` 把它列进"系统是否健康"的四项之一（`:246` 明确写"四项全绿 = 这个系统当前是好的"）。

3. 执行方看到红的第一反应会是"环境坏了"，而 `doctor` 明明 11 项通过——这会浪费一轮排查。

#### 修法选项

| 方案 | 做法 | 优点 | 缺点 | 成本 |
|---|---|---|---|---|
| **A. 补 Bearer（推荐）** | `cmd_smoke` 读 `read_env_token()`，构造 `Request` 带 `Authorization: Bearer <token>`；`--no-auth` 时不带 | 测到真实鉴权路径；复用已有函数；改动 < 20 行 | 需要处理"没有 token 且没开 no-auth"的错误文案 | 低 |

| C. 用 `-NoAuth` 作为文档默认 | 改 README 让用户自己加参数 | 不改代码 | 把缺陷转嫁给用户；台账仍不实 | 极低 |

**推荐 A。** 理由：smoke 的价值就在于"用真实配置跑一遍"，去掉鉴权就失去意义。

### 3.2 P1-02：SSRF 断言是假阳性

#### 现象

`run.py:200-210` 的第三步：

```python
try:
    urlreq.urlopen(f"{base}/detect?url=http://127.0.0.1:{a.port}/health",
                   timeout=10)
    print("FAIL: SSRF 守卫失效：内网 URL 没有被拒绝", file=sys.stderr)
    return 1
except (URLError, OSError):
    pass
print("OK  SSRF 守卫拦住了内网 URL")
```

#### 根因

`URLError` 是 `HTTPError` 的父类。**401、500、连接被拒、DNS 失败、超时，全部落进 `except`**。也就是说：

- 守卫真的拦住了（400）→ 打印 OK ✅
- 守卫**没有**拦住，但请求因为别的原因失败（401/500/超时）→ **还是打印 OK** ❌
- 只有"请求成功返回 200"才会判 FAIL

这意味着这个断言只覆盖了"服务完全正常且守卫失效"这一种极端情况，**其它所有失败路径都被误判为通过**。

更糟的是：由于 P1-01，当前默认配置下这一步**恰好**走的是 401 分支——它会打印 "OK SSRF 守卫拦住了内网 URL"，给出完全错误的信心。

#### 影响面

这是"门禁本身不可信"的典型。`docs/项目规格.md` §7 末尾专门有一段"入口守卫的两种拒绝语义（别混）"，说明作者很清楚 400 与 502 的区别；但 smoke 的代码没有把这份认知编码进去。

#### 修法（推荐：精确断言状态码）

```python
import urllib.error

try:
    with urlreq.urlopen(req, timeout=10) as r:
        body = r.read()[:200]
    print(f"FAIL: SSRF 守卫失效：内网 URL 返回了 200（body={body!r}）", file=sys.stderr)
    return 1
except urllib.error.HTTPError as e:
    # 规格文档 §7：私网/回环/保留地址 → 400 invalid-request；
    # 域名解析失败 → 502 transport。两者都算"拦住了"，其余不算。
    if e.code not in (400, 502):
        print(f"FAIL: SSRF 守卫返回 {e.code}，期望 400 或 502（见 docs/项目规格.md §7）",
              file=sys.stderr)
        return 1
    print(f"OK  SSRF 守卫拦住了内网 URL（HTTP {e.code}）")
except (urllib.error.URLError, OSError) as e:
    print(f"FAIL: 请求内网 URL 时连接异常（{e}）——无法证明守卫生效", file=sys.stderr)
    return 1
```

#### 验收标准

- **正向**：默认配置 + 正确 token 跑 smoke → 第三步输出 `OK SSRF 守卫拦住了内网 URL（HTTP 400）`。
- **负向 1**（验证断言能变红）：把 `--token` 换成错误值 → 第三步必须 **FAIL**，而不是 OK。
- **负向 2**：把服务端 SSRF 守卫临时改成放行（只在本机实验分支）→ 第三步必须 FAIL 并且输出 200 的 body 片段。
- **单元**：新增 `test_smoke_ssrf_assertion_rejects_unexpected_status`：替身 `urlopen` 抛 `HTTPError(401)` → 断言 `cmd_smoke` 返回非 0。

**这一条是 v7.0 的"门禁自测"样板**：门禁脚本必须证明自己会在该红的时候红。项目已有 `scripts/gates.selftest.mjs` 做类似的事（注入漂移 → 必须变红），smoke 也应该有一份。

```ts
test('theme toggle switches, persists, and keeps aria-pressed in sync', async ({ page }) => {
  await page.goto('/', { waitUntil: 'networkidle' });
  const toggle = page.locator('button.icon-button[aria-label]').first();
  const before = await page.evaluate(() => document.documentElement.dataset.theme);
  await toggle.click();
  const after = await page.evaluate(() => document.documentElement.dataset.theme);
  expect(after).not.toBe(before);
  await expect(toggle).toHaveAttribute('aria-pressed', after === 'dark' ? 'true' : 'false');
  await page.reload({ waitUntil: 'networkidle' });
  expect(await page.evaluate(() => document.documentElement.dataset.theme)).toBe(after);
  expect(await page.evaluate(() => localStorage.getItem('cf-theme'))).toBe(after);
});

test('language switch maps zh and en routes both ways', async ({ page }) => {
  await page.goto('/how-it-works/', { waitUntil: 'networkidle' });
  const link = page.locator('a.icon-button[hrefLang]').first();
  await expect(link).toHaveAttribute('href', '/en/how-it-works/');
  await link.click();
  await page.waitForLoadState('networkidle');
  expect(new URL(page.url()).pathname).toBe('/en/how-it-works/');
  await expect(page.locator('a.icon-button[hrefLang]').first()).toHaveAttribute('href', '/how-it-works/');
});

test('mobile menu expands and its links are clickable at 360px', async ({ page }) => {
  await page.setViewportSize({ width: 360, height: 800 });
  await page.goto('/', { waitUntil: 'networkidle' });
  const details = page.locator('details.mobile-menu');
  await expect(details).not.toHaveAttribute('open', '');
  await details.locator('summary').click();
  await expect(details).toHaveAttribute('open', '');
  const links = details.locator('nav a');
  await expect(links).toHaveCount(6);
  for (let i = 0; i < 6; i += 1) {
    const box = await links.nth(i).boundingBox();
    expect(box).not.toBeNull();
    expect(box!.height).toBeGreaterThan(24);
  }
});
```

**注意**：`ThemeToggle` 的 `aria-pressed` 语义是"dark 是否按下"，所以断言必须按 `after === 'dark'` 分支写，不能硬编码 `true`。这是本项目"断言要跟实现语义一致"的一贯要求。

#### 验收标准

```powershell

```

**回归风险**：低。三个用例都是只读断言，不改产品代码。唯一需要注意的是 `details` 的 `open` 属性在 Playwright 里是布尔属性，用 `toHaveAttribute('open', '')` 判断。

### 3.7 P2-05：`RATE_LIMITED` 是一个契约空洞

#### 现象

`solver/errors.py:29`：

```python
RATE_LIMITED = "rate-limited"   # **预留值**：当前没有按 host 限流，不会产生（见下）
```

- 客户端代码说"这个码会来，我要据此 failover"。

#### 为什么 v7.0 要做

不是因为"应该有个限流"，而是因为 **R9b 证明了出口信誉会被打坏**：

> 同一出口连续打同一站 12 次后，60s 解不出。（`policy.md` §2、状态文档 §4.1）

当前唯一的缓解是**人的纪律**。纪律的问题是：它不会在凌晨三点的自动化任务里生效。

#### 方案对比

| 方案 | 算法 | 内存 | 边界行为 | 落地复杂度 |
|---|---|---|---|---|
| A. 固定窗口计数 | `count[host] += 1`，按分钟重置 | O(域数) | 窗口边界双倍突发 | 最低 |
| B. 滑动窗口日志 | 存最近 N 次时间戳 | O(请求数) | 精确 | 中 |
| **C. 令牌桶（推荐）** | `tokens = min(cap, tokens + rate*dt)` | O(域数) | 平滑，允许短突发 | 低 |

推荐 **C**，理由是：域数上限已有（≤4096，`docs/项目规格.md` §1 的规模假设），每域两个 float 的内存在预算内；令牌桶的"允许短突发"特性正好匹配"预热/续期会连打两次"的真实模式。

#### 设计要点

- **默认关闭**：`--rate-per-host 0`（0 = 不启用），保证现有行为零变化。
- **只对冷求解计数**：缓存命中不消耗令牌。否则预热会把桶打空。
- **落点**：新建 `solver/ratelimit.py`（纯函数 + 有界状态），在 `Solver.solve` 的准入之前调用；错误用 `SolveError(ErrorCode.RATE_LIMITED, ...)`。
- **observability**：`/metrics` 增 `ratelimit_rejected_total{host}`（走现有 top-20 基数限制）。
- **文档**：`docs/API.md` 去掉"预留，默认未启用"，改成"`--rate-per-host > 0` 时产生"；`docs/项目规格.md` 的启动参数表加一行。
- **Go 客户端**：无需改代码——它已经处理了这个码。但要补一条**契约用例**证明"服务端开启限流后，Go 池会 failover 而不是摘节点"。

#### 验收标准

- 默认（`--rate-per-host 0`）下，全部现有用例与压测结果不变（回归）。
- 开启后：同一 host 第 N+1 次请求返回 `429 + error_code=rate-limited + stage=admit`。
- 缓存命中不消耗令牌（专门用例）。
- `/metrics` 出现 `ratelimit_rejected_total`。
- 新增用例 ≥ 8 条（默认关、单域触发、多域隔离、命中不计数、令牌恢复、突发容量、Go 契约、错误码映射）。

**风险**：如果实现成"全局桶"，会误伤多域并发。必须**按域**建桶，且桶的状态要有界（域数上限 + LRU 淘汰）。

## 4. v7.0 升级方案

### 4.1 主题与目标

**主题**：从"能跑"到"可信赖"。

一句话定义 v7.0 的成功：**当执行方跑完 `verify`，他不需要再问"是不是漏了什么"；当冷请求打进来，它不需要先启动一个 1.2GB 的浏览器；当某个域被连续重试，系统自己会踩刹车。**

### 4.2 三条主线 + 一条贯穿线

| 主线 | 目标 | 对应问题 | 成功判据 |
|---|---|---|---|
| **A. Trust** | 门禁自洽、文档可执行 | P1-01、P1-02、P2-01、P2-02 | `verify` 全绿且包含 smoke；改坏版本行/SSRF 断言会红；README 的每条命令都真实存在 |
| **B. Footprint** | 冷启动可负担（资源维度） | 瓶颈一 | `doctor` 不再 WARN；cfsolve 可被装配；冷求解可选 72MB 无浏览器路径；装配步骤有可执行向导 |
| **C. Resilience** | 出口可保护 | P2-05 | 开启限流后单域不被连续重试；缓存命中不消耗令牌；Go 池行为符合契约 |
| **D. Experience** | 交互防回归 | P2-03 | 22 条 E2E 全绿；三类交互有断言 |

### 4.3 方案对比矩阵

#### 主线 A：门禁自洽

| 方案 | 技术可行性 | 开发成本 | 维护成本 | 收益 | 风险 | 可衍生性 | 总分 |
|---|---:|---:|---:|---:|---:|---:|---:|

| **A2 门禁闭环（smoke 修复 + 断言行修正 + verify 纳入 + 文档对账）** | 5 | 4 | 4 | 5 | 4 | 4 | **26** |
| A3 变异门禁（对关键脚本做变异测试） | 3 | 2 | 3 | 4 | 3 | 4 | **19** |

> 评分口径：1–5，成本越低分越高；总分仅用于对比，不作绝对判据。

**推荐 A2**。A3 的变异测试很诱人，但当前项目已经有 `scripts/gates.selftest.mjs`（21 条负向注入）覆盖了"门禁能变红"的核心诉求；再引入变异框架属于"为同一个目标买第二份保险"。**A2 做完之后，如果还有精力，优先做 C 而不是 A3。**

#### 主线 B：冷启动资源优化

> **前提**：延迟由 CF 的 PoW 预算决定，本主线**不承诺降低求解耗时**（能压的只有 ≈1.5–2s 的人类行为模拟段）。目标是让"72MB 无浏览器"这条路可以被装配，从而降低内存占用与部署门槛——在 4 worker 的 3.5GB 预算里，这就是"能不能多开两个 worker"的问题。

| 方案 | 技术可行性 | 开发成本 | 维护成本 | 收益 | 风险 | 可衍生性 | 总分 |
|---|---:|---:|---:|---:|---:|---:|---:|
| B1 只改文档（把构建步骤写清楚） | 5 | 5 | 5 | 1 | 5 | 1 | **22** |
| **B2 装配向导（`run.py cfsolve-setup`：检测工具链 → 打印可执行步骤 → 校验产物）** | 4 | 4 | 4 | 4 | 4 | 4 | **24** |
| B3 预构建分发（CI 产物 / 对象存储） | 2 | 2 | 2 | 5 | 2 | 3 | **16** |

**推荐 B2**。B3 会引入"分发渠道 + 版本对齐 + 供应链信任"三个新问题，而本项目的定位是自托管研究工程，不是发行版。B2 的价值在于把"需要读三份文档才能拼出来的构建流程"变成"一条命令告诉你缺什么"。

**B2 的具体形态**（不下载任何东西，只诊断 + 引导）：

```text
python run.py cfsolve-setup
  ✓ 检测 Rust 工具链（cargo --version）
  ✓ 检测 MSVC / CMake / NASM / libclang（缺哪个说哪个，给安装链接）
  ✓ 检测 cfsolve 仓库是否存在（默认 ../cfsolve，可用 --repo 指定）
  ✓ 检测本地补丁是否可干净应用（git apply --check）
  ✓ 检测已有的 challenge/capture-proxy 产物（--cfsolve-bin 指向它）
  → 输出"下一步该跑什么"，不替用户执行构建
```

**为什么不做成"自动构建"**：构建需要 MSVC 环境变量（vcvars64）与网络拉取 crate，自动化脚本在别人的机器上大概率失败，而且失败时的可诊断性远不如"你把这三步贴进开发者命令行"。**向导的职责是消歧，不是代替。**

#### 主线 C：韧性

| 方案 | 技术可行性 | 开发成本 | 维护成本 | 收益 | 风险 | 可衍生性 | 总分 |
|---|---:|---:|---:|---:|---:|---:|---:|

**推荐 C1 + C3 的轻量版**。C2 与 `solver/proxypool.py` 已有的"评分 + 冷却"重叠，属于重复造轮子；C1 是把已有契约码真正兑现；C3 只需要在 `tests/` 里加一个 `fault_inject` fixture（monkeypatch 缓存层抛 `sqlite3.OperationalError`），成本很低但能验证 R13 的有界重试真的有效。


### 7.4 关于"覆盖率拉满 100%"的口径说明

本项目**不把 100% 作为目标**，这是刻意的，不是偷懒。原因写在 `policy.md` 的"门槛口径"一节：

- 覆盖率门槛是 **floor（防向下漂移）**，不是 KPI。加代码不加测试就会掉下 min，这正是想要的信号。
- `captchas/` 的多数分支需要 **专有二进制 + 许可证 + 真实挑战页**，离线环境不可达。把门槛拉到 100% 只会逼出"无断言测试"或"mock 掉被测对象"，两者都是假绿。
- `solver/service.py` 的未覆盖行里有一批是**不可达的防御分支**（坏行、WS API 不可用、异常早退）。给它们写测试需要人为构造畸形状态，收益低于维护成本。

**如果要提高覆盖率，正确顺序是**：

1. 先做 **T-09**（把 `captchas/` 里真正可离线测的纯函数拆出来测）——这是唯一能在不碰真机的前提下把数字做实的路径。
2. 再做 **T-11**（逐段标注 `unreachable` / `needs-real` / `worth-testing`）——让"没测"变成"有理由地没测"。
3. 最后才考虑给 `worth-testing` 那一类补用例。

**明确不允许**：为了让覆盖率数字好看而写空断言、跳过真实路径、或把被测对象 mock 掉。`policy.md` 与全局指令都禁止这类做法。
